# Coze 平台使用教程

> 学了 Prompt Engineering、RAG、Agent，但怎么把它们组合成一个真正能用的 AI 应用？Coze（扣子）是**目前市面上应用最广泛的 AI 智能体开发平台**，以直观的可视化界面和丰富的功能模块，让你像搭积木一样把 LLM、知识库、插件、工作流串联起来，快速构建和部署智能助手。
>
> 实战案例详见：[[Coze实战案例]]

## 一、Coze 是什么

### 1.1 平台定位

**Coze（扣子）** 是字节跳动推出的 AI Bot 开发平台，核心定位是**让非程序员也能构建 AI 应用**。

```
传统开发 AI 应用：
  写代码 → 调 API → 搭后端 → 做前端 → 部署 → 运维
  （需要前端 + 后端 + 算法工程师，周期以周/月计）

Coze 开发 AI 应用：
  配置 Prompt → 选插件 → 搭工作流 → 发布
  （一个人几小时搞定）
```

### 1.2 Coze 能做什么

| 应用类型 | 示例 | 核心技术 |
|---------|------|---------|
| **智能客服** | 电商答疑、产品咨询 | 知识库 + 意图识别 + RAG |
| **内容生成** | 文案撰写、每日AI简报 | 大模型 + 工作流编排 + 多源插件 |
| **信息查询** | 天气查询、股票查询 | 插件 + Function Calling |
| **游戏助手** | LOL 攻略查询 | 知识库检索 + 角色扮演 |
| **多媒体创作** | 视频自动生成 | 工作流 + 图像/视频生成插件 |

## 二、核心概念与组件

### 2.1 Bot（智能体）

Bot 是 Coze 的基本单位，一个 Bot = 一个完整的 AI 应用。

```
Bot 的组成部分：
┌──────────────────────────────────────┐
│  人设与回复逻辑（System Prompt）      │  ← 定义角色、技能、限制
├──────────────────────────────────────┤
│  插件（Plugins）                      │  ← 工具能力（搜索、计算、API等）
├──────────────────────────────────────┤
│  知识库（Knowledge Base）             │  ← 专属数据（文档、表格等）
├──────────────────────────────────────┤
│  工作流（Workflow）                   │  ← 复杂业务逻辑编排
├──────────────────────────────────────┤
│  对话体验（开场白、快捷指令等）        │  ← 用户交互设计
└──────────────────────────────────────┘
```

### 2.2 人设与回复逻辑（System Prompt）

这是 Bot 的"灵魂"，用结构化的 Prompt 定义角色。Coze 推荐使用 **角色-技能-限制** 三段式结构：

```markdown
# 角色
你是一位专业的跨境电商答疑小助手，精通跨境电商领域的各类知识。

## 技能
### 技能 1: 基于上下文解答问题
1. 严格依据提供的上下文内容进行回答。
2. 回答需精准、简洁、有条理。

### 技能 2: 答案优化
1. 若检索出的答案比较简单，需进行优化，但不改变核心内容。

## 限制
- 仅回答与跨境电商相关的问题。
- 回答内容必须符合上述技能要求的格式和规范。
```

**Prompt 编写关键技巧**（详见 [[Prompt Engineering与CoT]]）：

| 要素 | 说明 | 示例 |
|------|------|------|
| **角色定义** | 明确身份、经验年限 | "你是一位拥有10年经验的沟通专家" |
| **技能拆分** | 每个技能独立描述流程 | 技能1 语气把控、技能2 内容构建 |
| **输出格式** | 指定回复模板 | "【开场寒暄】…【表达理解】…" |
| **硬性限制** | 防止越界行为 | "避免使用'不''拒绝'等直接负面词汇" |

### 2.3 插件（Plugin）

插件是 Bot 的"工具"，让 LLM 能够调用外部系统。Coze 拥有**全平台最丰富的插件生态**，支持官方插件和自定义插件。

**官方插件**：平台提供的即用型插件

| 插件类型 | 功能 | 典型插件 |
|---------|------|---------|
| 联网搜索 | 搜索实时信息 | search_url（必应搜索）、RSS 订阅 |
| 地图服务 | 位置查询、周边搜索 | 高德地图 Search_around |
| 天气查询 | 获取天气预报 | 墨迹天气 DayWeather |
| 计算工具 | 数学运算 | 简易计算器 calculate |
| 代码托管 | 追踪开源项目 | GitHub 插件 |
| 学术搜索 | 获取最新论文 | arXiv 插件 |

**自定义插件**：用 Python 编写自己的工具（详见 [[#三、自定义插件开发详解]]）。

### 2.4 知识库（Knowledge Base）

知识库让 Bot 能基于专属数据回答问题，本质是**内置 RAG**。

```
知识库工作流程：
  用户问题 → 向量检索 → 召回相关文档片段 → 拼接上下文 → LLM 生成答案
```

详细原理见：[[RAG]]、[[向量数据库]]、[[重排序Reranking]]

### 2.5 工作流（Workflow）

工作流是 Coze 的**核心编排能力**，适合处理复杂多步骤业务。通过可视化拖拉拽节点，编排 Bot 的执行逻辑。

**工作流节点类型**：

| 节点类型 | 功能 | 使用频率 |
|---------|------|---------|
| **开始节点** | 接收用户输入 | 必用 |
| **大模型节点** | 调用 LLM 处理/生成 | ⭐⭐⭐ |
| **插件节点** | 执行工具调用 | ⭐⭐⭐ |
| **知识库检索** | 从知识库召回相关内容 | ⭐⭐ |
| **选择器节点** | 条件分支判断（if/else） | ⭐⭐⭐ |
| **代码节点** | 自定义 Python/JS 代码 | ⭐⭐ |
| **批处理节点** | 对数组逐条并发执行 | ⭐⭐ |
| **图像/视频生成** | AI 生成多媒体 | ⭐ |
| **结束节点** | 返回最终结果 | 必用 |

## 三、自定义插件开发详解

### 3.1 插件结构

Coze 自定义插件的核心是**一个 Python 函数**：

```python
from runtime import Args

def handler(args: Args) -> dict:
    """
    插件必须导出 handler 函数，这是 Coze 平台的入口约定。

    参数：args - Coze 传入的运行时上下文
        args.input  - 输入参数（在插件 manifest 中声明）
        args.logger  - 日志记录器（可在 Coze 后台查看）

    返回：dict - 插件的输出结果
    """
    # 1. 获取输入
    param = args.input.param_name

    # 2. 业务逻辑
    result = do_something(param)

    # 3. 返回结果
    return {"output_field": result}
```

### 3.2 完整示例：天气查询插件

```python
from runtime import Args
import requests

def handler(args: Args):
    """
    天气查询插件：根据城市名称查询天气信息
    输入：location (城市名，如"北京")
    输出：{high, low, weather, week}
    """
    # 1. 解析输入
    location = args.input.location.strip()

    # 2. 城市编码映射
    city_code_map = {
        "北京": "101010100",
        "天津": "101030100"
    }
    city_code = city_code_map.get(location)
    if not city_code:
        args.logger.warning(f"不支持的城市: '{location}'")
        return {"high": None, "low": None, "weather": None, "week": None}

    # 3. 调用天气 API
    url = f"http://t.weather.itboy.net/api/weather/city/{city_code}"
    try:
        response = requests.get(url, timeout=5)
        response.raise_for_status()
        data = response.json()

        if data.get("status") != 200:
            raise ValueError("API 返回非 200 状态")

        forecast = data["data"]["forecast"][0]
        return {
            "high": forecast["high"],     # "高温 7℃"
            "low": forecast["low"],       # "低温 -1℃"
            "weather": forecast["type"],  # "晴"
            "week": forecast["week"]      # "星期二"
        }
    except Exception as e:
        args.logger.error(f"查询失败 '{location}': {e}")
        return {"high": None, "low": None, "weather": None, "week": None}
```

`★ Insight ─────────────────────────────────────`
**插件开发的三个关键点**：(1) `args.input.xxx` 获取用户输入参数——这是 Coze 平台的约定接口；(2) 所有异常都要 catch 并返回空值结构——插件崩溃会导致整个 Bot 挂掉；(3) `args.logger` 记录日志——这在调试自定义插件时非常有用，可以在 Coze 后台查看。
`─────────────────────────────────────────────────`

### 3.3 插件开发最佳实践

| 最佳实践 | 说明 |
|---------|------|
| **永远有兜底返回** | 插件挂 = Bot 挂，所以任何异常都要 catch |
| **输出结构固定** | 不管成功失败，返回的 dict 结构要一致 |
| **参数声明要清晰** | 在插件 manifest 中写清楚每个参数的类型和描述 |
| **给 LLM 写好描述** | 插件描述会被 LLM 看到，影响它何时调用你的插件 |
| **网络请求设 timeout** | 防止插件卡死，影响整个工作流 |

## 四、Bot 开发方法论

### 4.1 复杂度分级

```
Level 1: 纯 Prompt Bot
  └── 适用：翻译、改写、角色扮演等纯文本任务

Level 2: Prompt + 知识库 Bot
  └── 适用：产品问答、游戏攻略等需要专属知识的任务

Level 3: Prompt + 知识库 + 插件 Bot
  └── 适用：需要实时信息（天气、搜索、论文）的任务

Level 4: 工作流 Bot（单线流程）
  └── 适用：意图识别 + 分流 + 多路径处理

Level 5: 工作流 Bot（多媒体生成）
  └── 适用：图像、视频等多媒体内容全自动生成
```

### 4.2 Prompt 设计最佳实践

| 实践 | 说明 | 反例 | 正例 |
|------|------|------|------|
| **角色要具体** | 有经验年限、有专长领域 | "你是一个助手" | "你是拥有10年经验的跨境电商专家" |
| **技能要可操作** | 每个技能有明确步骤 | "善于沟通" | "先理解对方→再说明限制→最后给替代方案" |
| **输出给模板** | 指定回答的格式框架 | "给出建议" | "【开场寒暄】…【替代方案】…【结尾祝福】…" |
| **限制要硬** | 禁止行为明确列出来 | 无限制 | "不超过300字""避免使用否定词汇" |

### 4.3 工作流设计原则

```
1. 职责单一：每个节点只做一件事
2. 错误兜底：每个分支都要有终结点
3. 格式显式：节点间的数据格式要明确声明
4. 先简后繁：先用简单流程跑通，再逐步加节点
5. 可调试性：关键节点加日志（代码节点 print）
```

### 4.4 Coze 的优势与局限性

#### 优势

| 优势 | 说明 |
|------|------|
| **强大的插件生态** | 全平台最丰富的插件库，轻松接入外部服务与数据源，功能高度可扩展 |
| **直观的可视化编排** | 低门槛的拖拽式工作流，无需深厚编程知识即可构建复杂逻辑 |
| **灵活的提示词控制** | 精确的角色设定 + 结构化 Prompt，实现高度定制化输出；支持提示词管理和模板 |
| **便捷的多平台部署** | 一键发布到飞书、微信、豆包等主流平台，且平台生态圈在不断扩大 |
| **丰富的社区资源** | 官方模板一键复制、智能体社区琳琅满目、详细教程文档 |

#### 局限性

| 局限性 | 说明 |
|--------|------|
| **不支持 MCP** | 这是目前最致命的短板。尽管插件市场极其丰富，但不支持 MCP（Model Context Protocol）可能成为限制其发展的枷锁。如果放开，将是又一杀手锏 |
| **部分插件配置复杂** | 需要 API Key 等高级参数的插件，用户需一定技术背景；复杂工作流编排也需要 JS/Python 基础 |
| **无法直接导入编排 JSON** | 付费版支持导出导入，但格式是 zip（只能在扣子内部使用），不像 Dify/n8n 那样支持通用 JSON 文件。取巧方案：在编排界面 Ctrl+A 全选 → Ctrl+C 复制 → 到另一个工作流粘贴 |
| **学习曲线** | 零基础用户可以快速上手简单 Bot，但要做出复杂的工作流编排，还是需要一定的编程思维 |

## 五、面试高频问题

### Q1：Coze 是什么？它解决了什么问题？

> Coze（扣子）是字节跳动推出的 AI Bot 开发平台，让非程序员通过**配置 Prompt、选择插件、搭建工作流**就能构建和发布 AI 应用。它解决了 AI 应用开发门槛高（需要前端+后端+算法）、周期长（数周到数月）、维护难的问题，实现了 AI 应用的民主化。

### Q2：Coze 的核心组件有哪些？各有什么作用？

> Coze 的核心组件：(1) **Bot**——基本单位，一个完整的 AI 应用；(2) **人设 Prompt**——定义 Bot 的角色、技能、限制；(3) **插件**——Bot 的工具，让 LLM 调用外部系统（官方插件 + 自定义 Python 插件）；(4) **知识库**——Bot 的专属记忆，上传文档即可实现 RAG 问答；(5) **工作流**——可视化编排复杂业务逻辑的节点图。

### Q3：Coze 的知识库和 RAG 有什么关系？

> Coze 的知识库本质就是**内置的 RAG 系统**。用户上传文档后，Coze 自动完成文本切分、向量化、存储。当用户提问时，自动进行向量检索、召回相关片段、拼接到 LLM 上下文中。开发者只需写好知识库相关的 Prompt（如"无结果时怎么回复"），无需关心底层 RAG 的技术细节。

### Q4：什么是工作流？什么时候应该用工作流而不是纯 Prompt？

> 工作流是 Coze 的可视化编排工具，用节点图串联多个 LLM 调用、插件执行、代码处理。**应该用工作流的场景**：(1) 需要意图识别分流——打招呼、专业问题、转人工走不同逻辑；(2) 需要多步推理——先查 A 再根据 A 的结果决定查 B；(3) 需要格式转换——节点间数据格式不匹配需要代码中转；(4) 需要批处理——对数组逐条执行相同操作（如批量生成图片）。

### Q5：自定义插件的 handler 函数有哪些注意事项？

> (1) **函数名必须是 `handler`**——这是 Coze 入口约定；(2) **参数是 `args: Args`**——通过 `args.input.xxx` 获取输入，`args.logger` 打日志；(3) **必须返回 dict**——且成功和失败时的结构要一致；(4) **所有异常都要 catch**——插件崩溃会导致整个 Bot 不可用；(5) **网络请求设 timeout**——防止插件卡死。

### Q6：设计一个电商客服 Bot，你会如何设计 Prompt 和工作流？

> 设计思路：(1) **意图识别插件**将用户输入分为打招呼、找人工、退换货、专业咨询四类；(2) **打招呼**直接友好回复；(3) **找人工**返回客服链接；(4) **退换货**走专门的流程模板；(5) **专业咨询** → 知识库检索 → 有结果则 RAG 回答，无结果则 LLM 结合自身知识补充并标注"仅供参考"。Prompt 采用角色-技能-限制三段式，限制中明确只回答电商相关问题。

### Q7：Coze 有哪些优势和局限性？

> **优势**：(1) 全平台最丰富的插件生态；(2) 直观的低代码可视化编排；(3) 灵活的 Prompt 控制 + 提示词模板管理；(4) 一键多平台发布（飞书、微信、豆包等）；(5) 丰富的社区模板和教程。
>
> **局限性**：(1) **不支持 MCP**——最致命的短板，限制了与外部 Agent 生态的互通；(2) 复杂插件配置仍需技术背景；(3) 导出格式为私有 zip，不能像 Dify 那样导出通用 JSON 编排文件；(4) 高级工作流编排有一定学习曲线。
