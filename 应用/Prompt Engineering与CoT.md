# 提示词工程与思维链

> 量化技术解决了"模型跑不起来"的问题，现在来解决"怎么让模型更好地回答问题"**。Prompt Engineering（提示词工程）是通过设计输入文本来引导模型输出的技术，是大模型应用的基础技能。Chain of Thought（思维链）是其中最重要的推理技巧。

---

## 一、Prompt Engineering 基础

### 1.1 什么是 Prompt Engineering

**Prompt Engineering**：通过设计、优化输入给大模型的文本（Prompt），来获得更好输出的技术。

```
差的 Prompt：
  "翻译"
  → 模型不知道翻译什么、翻译成什么语言

好的 Prompt：
  "请将以下英文翻译成中文：Hello, how are you?"
  → 模型准确翻译：你好，你怎么样？
```

### 1.2 Prompt 的基本组成

| 组成部分 | 作用 | 示例 |
|---------|------|------|
| **指令（Instruction）** | 告诉模型做什么 | "请翻译以下文本" |
| **上下文（Context）** | 提供背景信息 | "你是一位专业的医学翻译" |
| **输入（Input）** | 需要处理的内容 | "Heart failure is..." |
| **输出格式（Output Format）** | 指定回答格式 | "请用 JSON 格式输出" |

**完整示例**：

```
【角色】你是一位资深的 Python 开发工程师，擅长代码审查。
【任务】请审查以下代码，找出潜在的 bug 和改进建议。
【输入】
def fibonacci(n):
    if n <= 1:
        return n
    return fibonacci(n-1) + fibonacci(n-2)
【输出格式】请按以下格式回答：
1. 问题描述
2. 修复建议
3. 优化后的代码
```

### 1.3 Prompt 设计原则

| 原则 | 说明 | 示例 |
|------|------|------|
| **明确具体** | 避免模糊指令 | "总结这篇文章" → "用 3 句话总结这篇文章的核心观点" |
| **提供示例** | Few-shot 比 Zero-shot 效果好 | 给几个输入输出的例子 |
| **分步引导** | 复杂任务拆解 | "先分析问题，再给出解决方案" |
| **指定格式** | 控制输出结构 | "请用 JSON 格式输出" |
| **设定角色** | 让模型进入特定模式 | "你是一位医学专家..." |

## 二、Zero-shot vs Few-shot

### 2.1 Zero-shot Prompting

**不提供示例**，直接让模型执行任务。

```
Zero-shot Prompt:
"将以下英文翻译成中文：The weather is nice today."

模型输出:
"今天天气很好。"
```

**适用场景**：简单任务，模型本身能力足够。

### 2.2 Few-shot Prompting

**提供几个示例**，让模型学习模式后再执行任务。

```
Few-shot Prompt:
"请将英文翻译成中文。

示例1:
英文: Hello, how are you?
中文: 你好，你怎么样？

示例2:
英文: The cat is on the table.
中文: 猫在桌子上。

示例3:
英文: The weather is nice today.
中文:"

模型输出:
"今天天气很好。"
```

**为什么 Few-shot 更好？**

| 方面 | Zero-shot | Few-shot |
|------|----------|---------|
| 模型理解 | 可能误解任务 | 示例明确任务 |
| 输出格式 | 不确定 | 示例固定格式 |
| 一致性 | 变化大 | 更一致 |
| 复杂任务 | 效果差 | 效果好 |

### 2.3 示例的选择

| 技巧 | 说明 |
|------|------|
| **多样性** | 示例覆盖不同情况 |
| **难度递进** | 从简单到复杂 |
| **格式一致** | 所有示例格式相同 |
| **数量适中** | 通常 3-5 个示例 |
| **相关性** | 示例和实际任务相关 |

`★ Insight ─────────────────────────────────────`
**示例的顺序也重要**：研究发现，Few-shot 示例的顺序会影响结果。把最相似的示例放在最后（靠近实际输入）通常效果更好，因为模型对最近的上下文更敏感。
`─────────────────────────────────────────────────`

## 三、Chain of Thought（思维链）

### 3.1 什么是 CoT

**Chain of Thought（CoT）**：让模型在回答问题前，先展示推理过程（"一步一步思考"），再给出最终答案。

```
普通 Prompt:
Q: 小明有 5 个苹果，给了小红 2 个，又买了 3 个，现在有几个？
A: 6 个

CoT Prompt:
Q: 小明有 5 个苹果，给了小红 2 个，又买了 3 个，现在有几个？
A: 让我们一步一步思考：
   1. 小明开始有 5 个苹果
   2. 给了小红 2 个，剩下 5-2=3 个
   3. 又买了 3 个，现在有 3+3=6 个
   答案：6 个
```

### 3.2 为什么 CoT 有效

| 原因 | 说明 |
|------|------|
| **分解复杂问题** | 把多步推理拆成单步 |
| **减少工作记忆压力** | 不需要同时记住太多中间结果 |
| **提供推理轨迹** | 中间步骤可以检查和纠错 |
| **模拟人类思考** | 人类也会"列算式"再计算 |

### 3.3 CoT 的变体
#### Zero-shot CoT

在 Prompt 中加入"Let's think step by step"：

```
Q: 一个农场有 15 只鸡，8 只鸭，鸡比鸭多几只？

Zero-shot CoT Prompt:
"请一步一步思考：一个农场有 15 只鸡，8 只鸭，鸡比鸭多几只？"

模型输出:
"让我们一步一步思考：
1. 鸡的数量：15 只
2. 鸭的数量：8 只
3. 鸡比鸭多：15 - 8 = 7 只
答案：7 只"
```

#### Few-shot CoT

提供带推理过程的示例：

```
Q: 小明买书花了 45 元，买笔花了 12 元，一共花了多少钱？

示例1:
Q: 小红买苹果花了 8 元，买橘子花了 5 元，一共花了多少钱？
A: 一步一步思考：
   1. 苹果：8 元
   2. 橘子：5 元
   3. 总计：8 + 5 = 13 元
   答案：13 元

示例2:
Q: 小明买书花了 45 元，买笔花了 12 元，一共花了多少钱？
A: 一步一步思考："
```

#### Self-Consistency（自一致性）

```
核心思想：多次采样，取多数票

1. 用 CoT 生成 N 个回答（温度 > 0）
2. 每个回答可能有不同的推理路径
3. 取出现次数最多的最终答案

例如：
  回答1: 推理过程A → 答案 6
  回答2: 推理过程B → 答案 6
  回答3: 推理过程C → 答案 7
  
  多数票：6（2/3）
```

#### Tree of Thoughts（思维树）

```
核心思想：让模型探索多条推理路径，选择最优的

        问题
       / | \
      /  |  \
    路径A 路径B 路径C
     |    |    |
    子步骤 子步骤 子步骤
     |    |    |
    继续   继续  继续
     ↓    ↓    ↓
    评估  评估  评估
       \  |  /
        选择最优
```

### 3.4 CoT 的适用场景

| 任务类型 | CoT 效果 | 示例 |
|---------|---------|------|
| **数学推理** | ⭐⭐⭐ | 应用题、几何证明 |
| **逻辑推理** | ⭐⭐⭐ | 逻辑谜题、推理判断 |
| **常识推理** | ⭐⭐ | 需要背景知识的问题 |
| **代码调试** | ⭐⭐⭐ | 找 bug、解释代码 |
| **多步决策** | ⭐⭐⭐ | 规划、策略 |
| **简单分类** | ⭐ | 不需要复杂推理 |

`★ Insight ─────────────────────────────────────`
**CoT 的本质是"外置工作记忆"**：大模型的上下文窗口就是它的"工作记忆"，CoT 把中间推理过程写出来，相当于在纸上列算式，而不是在脑子里算。这样即使模型"记性"有限，也能完成复杂的多步推理。
`─────────────────────────────────────────────────`

## 四、高级 Prompt 技巧

### 4.1 角色设定（Role Prompting）

```
普通 Prompt:
"解释什么是量子计算"

角色设定 Prompt:
"你是一位物理学教授，正在给本科生讲解量子计算。请用简单易懂的语言解释什么是量子计算，包括它和经典计算的区别，以及它的潜在应用。"
```

**角色设定的效果**：

| 方面 | 无角色 | 有角色 |
|------|--------|--------|
| 专业性 | 一般 | 更专业 |
| 语言风格 | 通用 | 符合角色 |
| 深度 | 表面 | 更深入 |

### 4.2 思维链 + 角色设定（组合使用）

```
"你是一位资深的数据分析师。请一步一步分析以下销售数据，找出：
1. 销售趋势
2. 异常点
3. 可能的原因
4. 改进建议

数据：[销售数据]
```

### 4.3 约束条件

```
"请用不超过 100 字总结这篇文章。

约束条件：
- 必须包含核心观点
- 不能使用专业术语
- 必须用中文"
```

### 4.4 输出格式控制

```
"分析以下用户评价的情感倾向，用 JSON 格式输出。

输入：'这个产品质量很好，但价格太贵了'

输出格式：
{
  "情感": "正面/负面/中性",
  "置信度": 0.0-1.0,
  "关键词": ["质量好", "价格贵"]
}"
```

### 4.5 迭代优化

```
第一轮: "写一首关于春天的诗"
         ↓ 效果不好
第二轮: "写一首七言绝句，主题是春天，要押韵，有意境"
         ↓ 还可以更好
第三轮: "模仿杜甫的风格，写一首七言绝句，描写江南春天的景色，
         要有'花'和'雨'的意象，押'ang'韵"
```

## 五、CoT 的局限性

### 5.1 不适用的情况

| 情况 | 说明 | 替代方案 |
|------|------|---------|
| 简单任务 | CoT 增加不必要的复杂度 | 直接回答 |
| 创意任务 | CoT 限制发散思维 | 直接生成 |
| 需要精确知识 | CoT 推理可能引入错误 | 检索增强（RAG） |

### 5.2 CoT 可能导致的问题

| 问题 | 说明 |
|------|------|
| **过度推理** | 简单问题也写一堆推理过程 |
| **错误传播** | 中间步骤错了，最终答案也错 |
| **幻觉** | 推理过程中编造不存在的事实 |
| **格式不一致** | 推理过程格式混乱 |

### 5.3 提高 CoT 可靠性的方法

```
1. Self-Consistency: 多次采样，多数票
2. CoT + RAG: 推理过程中检索事实
3. CoT + 验证: 推理后让模型验证每一步
4. 结构化 CoT: 要求模型用固定格式输出推理过程
```

---
## 六、总结

| 概念 | 核心要点 |
|------|---------|
| Prompt Engineering | 设计输入文本引导模型输出 |
| Zero-shot | 不提供示例，适合简单任务 |
| Few-shot | 提供示例，效果更好 |
| CoT | 让模型展示推理过程 |
| Self-Consistency | 多次采样取多数票 |
| Tree of Thoughts | 探索多条推理路径 |

**一句话记忆**：

> Prompt Engineering 就是"和 AI 说话的艺术"——说得越清楚、越有条理，AI 回答得越好。CoT 就是"让 AI 列算式"——把脑子里的推理过程写出来，答案就更准了。
