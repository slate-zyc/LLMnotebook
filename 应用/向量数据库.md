# 向量数据库：向量存储与检索

> 向量数据库是 RAG 系统的"仓库"——存储 Embedding 向量，并支持高效的相似度检索。选择合适的向量数据库直接影响 RAG 的检索速度和效果。

---

## 一、为什么需要向量数据库？

### 1.1 向量检索的挑战

普通数据库（MySQL、PostgreSQL）是为标量数据设计的：

```
传统数据库：
SELECT * FROM users WHERE age > 18 AND city = '北京'
→ 精确匹配，索引 B+Tree

向量数据库：
SELECT * FROM documents WHERE embedding SIMILAR TO [0.23, -0.15, ...] LIMIT 10
→ 近似最近邻（ANN），需要专门的索引结构
```

### 1.2 向量检索的核心需求

| 需求 | 说明 | 挑战 |
|------|------|------|
| **高维** | 向量维度通常 768~3072 | 维度灾难 |
| **大规模** | 可能有百万~十亿向量 | 内存/计算开销 |
| **实时** | 检索延迟要求毫秒级 | 需要高效索引 |
| **近似** | 找到最近邻而非精确匹配 | 精度 vs 速度权衡 |

### 1.3 近似最近邻（ANN）

精确最近邻搜索是 O(N) 复杂度，对于百万向量太慢。ANN 用索引结构加速：

```
精确搜索：遍历所有向量，找最相似的
  时间复杂度：O(N × D)  （N=向量数，D=维度）
  100万向量 × 1024维 ≈ 几秒

ANN 搜索：用索引结构快速定位候选
  时间复杂度：O(log N × D)
  100万向量 ≈ 毫秒级
```

## 二、向量数据库原理

### 2.1 核心索引算法

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **HNSW** | 层次化可导航小世界图 | 查询快，效果好 | 内存占用高 |
| **IVF** | 倒排索引 + 聚类 | 内存效率高 | 查询稍慢 |
| **PQ** | 乘积量化压缩 | 内存极低 | 精度损失 |
| **ScaNN** | 向量量化优化 | Google 出品，效果好 | 实现复杂 |

#### HNSW（Hierarchical Navigable Small World）

```
HNSW 索引结构：

第 0 层（最底层）：包含所有向量
  •───────•───────•───────•───────•
  |       |       |       |       |
  •───────•───────•───────•───────•
  |       |       |       |       |
  •───────•───────•───────•───────•

第 1 层：包含部分向量（稀疏）
  •───────────────•───────────────•
  |               |               |

第 2 层：包含极少向量（最稀疏）
  •───────────────────────────────•
  |                               |

查询过程：
1. 从最高层开始，找到最近的节点
2. 逐层下降，每层精细搜索
3. 最后在第 0 层找到精确的最近邻
```

#### IVF（Inverted File Index）

```
IVF 索引结构：

1. 先用 K-Means 将向量聚类成 N 个簇（如 1024 个）
2. 每个簇存储一个中心点和该簇的所有向量

簇 0：中心点 [0.1, 0.2, ...]
  ├── 向量 A
  ├── 向量 B
  └── 向量 C

簇 1：中心点 [0.3, 0.4, ...]
  ├── 向量 D
  └── 向量 E
...

查询过程：
1. 找到查询向量最近的 M 个簇中心（如 M=10）
2. 只在这 M 个簇中搜索最近邻
3. 搜索范围从 N 个向量缩小到 N × M/N 个
```

### 2.2 索引选择指南

```
小规模（<10万向量）：
  → Flat（暴力搜索）或 HNSW
  → 内存足够，直接暴力搜索也可以

中等规模（10万~100万向量）：
  → HNSW（推荐）或 IVF+PQ
  → HNSW 查询快，IVF+PQ 内存省

大规模（>100万向量）：
  → IVF+PQ 或 ScaNN
  → 需要压缩向量节省内存
```

## 三、常用向量数据库对比

### 3.1 主流方案

| 数据库 | 类型 | 特点 | 适用场景 |
|--------|------|------|---------|
| **FAISS** | 库 | Meta 出品，内存级，嵌入代码 | 中小规模，实验原型 |
| **Milvus** | 数据库 | 分布式，功能全面 | 大规模生产环境 |
| **Chroma** | 数据库 | 轻量级，Python 友好 | 快速原型开发 |
| **Qdrant** | 数据库 | Rust 实现，高性能 | 高性能需求 |
| **Pinecone** | 云服务 | 全托管，开箱即用 | 不想运维 |
| **Weaviate** | 数据库 | 支持多模态 | 多模态检索 |
| **pgvector** | 扩展 | PostgreSQL 扩展 | 已有 PG 基础设施 |

### 3.2 详细对比

#### FAISS

```python
# FAISS 使用示例
import faiss
import numpy as np

# 创建索引
dimension = 1024
index = faiss.IndexFlatIP(dimension)  # 内积索引

# 添加向量
vectors = np.random.random((10000, dimension)).astype('float32')
index.add(vectors)

# 搜索
query = np.random.random((1, dimension)).astype('float32')
k = 10  # 返回 top-10
distances, indices = index.search(query, k)
```

**特点**：
- ✅ 性能极好，C++ 实现
- ✅ 支持 GPU 加速
- ❌ 需要嵌入代码，不是独立服务
- ❌ 不支持过滤、持久化需要额外处理

#### Milvus

```python
# Milvus 使用示例
from pymilvus import connections, Collection, FieldSchema, CollectionSchema, DataType

# 连接
connections.connect("default", host="localhost", port="19530")

# 定义 schema
fields = [
    FieldSchema(name="id", dtype=DataType.INT64, is_primary=True, auto_id=True),
    FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=1024),
    FieldSchema(name="text", dtype=DataType.VARCHAR, max_length=200)
]
schema = CollectionSchema(fields)
collection = Collection("my_collection", schema)

# 创建索引
collection.create_index("embedding", {"metric_type": "IP", "index_type": "HNSW", "params": {"M": 16, "efConstruction": 256}})

# 搜索
results = collection.search(
    data=[query_embedding],
    anns_field="embedding",
    param={"metric_type": "IP", "params": {"ef": 64}},
    limit=10,
    output_fields=["text"]
)
```

**特点**：
- ✅ 分布式架构，支持水平扩展
- ✅ 功能全面（过滤、持久化、多副本）
- ✅ 支持多种索引类型
- ❌ 部署相对复杂

#### Chroma

```python
# Chroma 使用示例
import chromadb

# 创建客户端
client = chromadb.Client()  # 内存模式
# client = chromadb.PersistentClient(path="./chroma_db")  # 持久化模式

# 创建集合
collection = client.create_collection("my_collection")

# 添加文档
collection.add(
    documents=["这是第一个文档", "这是第二个文档"],
    embeddings=[embedding1, embedding2],
    metadatas=[{"source": "web"}, {"source": "pdf"}],
    ids=["doc1", "doc2"]
)

# 查询
results = collection.query(
    query_embeddings=[query_embedding],
    n_results=3
)
```

**特点**：
- ✅ Python 友好，API 简洁
- ✅ 轻量级，适合快速原型
- ❌ 不适合大规模生产
- ❌ 功能相对简单

#### Qdrant

```python
# Qdrant 使用示例
from qdrant_client import QdrantClient
from qdrant_client.models import Distance, VectorParams, PointStruct

# 创建客户端
client = QdrantClient(host="localhost", port=6333)

# 创建集合
client.create_collection(
    collection_name="my_collection",
    vectors_config=VectorParams(size=1024, distance=Distance.COSINE)
)

# 插入数据
client.upsert(
    collection_name="my_collection",
    points=[
        PointStruct(id=1, vector=embedding1, payload={"text": "文档1"}),
        PointStruct(id=2, vector=embedding2, payload={"text": "文档2"})
    ]
)

# 搜索
results = client.search(
    collection_name="my_collection",
    query_vector=query_embedding,
    limit=10
)
```

**特点**：
- ✅ Rust 实现，性能优秀
- ✅ 支持丰富的过滤条件
- ✅ 支持多向量、payload 索引
- ❌ 社区相对较小

### 4.1 场景匹配

```
原型开发 / 实验：
  → Chroma（最简单）或 FAISS（性能好）

中小规模生产（<100万向量）：
  → Qdrant（性能好）或 Milvus（功能全）

大规模生产（>100万向量）：
  → Milvus（分布式）或 Pinecone（托管）

已有 PostgreSQL：
  → pgvector（无需额外组件）

不想运维：
  → Pinecone（全托管）
```

## 五、向量数据库最佳实践

### 5.1 索引参数调优

```python
# HNSW 索引参数
index_params = {
    "M": 16,                # 每个节点的最大连接数
    "efConstruction": 256   # 构建时的搜索范围
}

# 查询参数
search_params = {
    "ef": 64                # 查询时的搜索范围
}

# 权衡：
# M 越大：内存占用越多，查询越准
# efConstruction 越大：构建越慢，索引质量越好
# ef 越大：查询越慢，结果越准
```

### 5.2 内存优化

```python
# 1. 降维：使用 PCA 或量化减少向量维度
# 2. 量化：使用 PQ 压缩向量
# 3. 稀疏化：只存储非零元素
# 4. 分片：将向量分布在多个节点

# 示例：使用 IVF+PQ 索引
index = faiss.IndexIVFPQ(
    quantizer,           # 量化器
    dimension,           # 向量维度
    nlist,               # 聚类中心数
    m,                   # PQ 子空间数
    nbits                # 每个子空间的位数
)
```

### 5.3 过滤策略

```python
# 方案 1：后过滤（先检索再过滤）
results = vector_db.search(query_embedding, top_k=100)
filtered = [r for r in results if r.metadata["category"] == "技术"]

# 方案 2：预过滤（用标量索引过滤后再检索）
results = vector_db.search(
    query_embedding,
    top_k=10,
    filter={"category": "技术"}  # 先过滤再检索
)

# 方案 3：混合索引（向量 + 标量联合索引）
# Milvus、Qdrant 支持
```

## 六、面试高频问题

### Q1：向量数据库和传统数据库有什么区别？

> 传统数据库为标量数据设计，支持精确匹配（B+Tree 索引）。向量数据库为高维向量设计，支持近似最近邻搜索（HNSW、IVF 索引）。核心区别：
> - 数据类型：标量 vs 高维向量
> - 查询方式：精确匹配 vs 近似相似度
> - 索引结构：B+Tree vs HNSW/IVF

### Q2：HNSW 和 IVF 有什么区别？怎么选？

> **HNSW**：基于图的索引，查询快但内存占用高。适合对查询延迟要求高的场景。
> **IVF**：基于聚类的索引，内存效率高但查询稍慢。适合大规模数据、内存受限的场景。
> 选择：中小规模选 HNSW，大规模选 IVF+PQ。

### Q3：如何评估向量数据库的性能？

> 关键指标：
> 1. **查询延迟**：毫秒级响应
> 2. **召回率**：Top-K 结果中包含真实最近邻的比例
> 3. **内存占用**：存储向量所需的内存
> 4. **构建时间**：创建索引所需的时间
> 
> 需要在延迟和召回率之间权衡。

### Q4：大规模向量检索如何优化？

> 优化方案：
> 1. **量化压缩**：使用 PQ 压缩向量，减少内存
> 2. **分片**：将向量分布在多个节点
> 3. **缓存**：缓存热点查询结果
> 4. **预过滤**：先用标量索引过滤再检索
> 5. **降维**：使用 PCA 降低向量维度

## 七、总结

**向量数据库的核心思想**：

> 存储高维向量，支持高效的近似最近邻搜索，是 RAG 检索的基础设施。

**选型建议**：

```
原型开发：Chroma
中小规模生产：Qdrant
大规模生产：Milvus
已有 PostgreSQL：pgvector
不想运维：Pinecone
实验性能：FAISS
```

**关键参数**：

| 参数 | 建议值 | 说明 |
|------|--------|------|
| HNSW.M | 16~32 | 平衡内存和精度 |
| HNSW.ef | 64~128 | 平衡查询速度和精度 |
| IVF.nlist | sqrt(N)~4*sqrt(N) | 聚类中心数 |
