# 推理优化：量化、KV Cache 与高效推理

> 大模型训练难，推理也不容易。一个 7B 模型推理时，光加载权重就要 14GB 显存（FP16），加上 KV Cache 随序列长度线性增长，长对话场景显存很快就不够用。推理优化就是在保证效果的前提下，让模型跑得更快、占更少显存。
>
> 本文讲解三种核心推理优化技术：量化、KV Cache、投机解码，并给出实际效果对比。

---

## 一、大模型推理的瓶颈

### 1.1 推理时显存占用

以 7B 模型 FP16 推理为例：

| 项目 | 占用 | 说明 |
|------|------|------|
| 模型权重 | ~14 GB | 7B × 2 字节（FP16） |
| KV Cache | 动态增长 | 取决于序列长度和 batch size |
| 激活值 | ~1-2 GB | 前向传播的中间结果 |
| **总计** | **16-20 GB+** | 长序列可能超过 24 GB |

### 1.2 推理时的计算瓶颈

LLM 推理是**自回归**的——每生成一个 token，都要跑一遍完整的前向传播：

```
生成第 1 个 token：完整前向传播（prefill，一次性处理所有输入 token）
生成第 2 个 token：完整前向传播（decode，只处理 1 个新 token）
生成第 3 个 token：完整前向传播
...
生成第 N 个 token：完整前向传播
```

**推理有两个阶段**：

| 阶段 | 输入 | 瓶颈 | 特点 |
|------|------|------|------|
| **Prefill** | 整个 prompt（如 2048 token） | 计算密集（GPU 算力） | 可并行，一次处理所有 token |
| **Decode** | 每次 1 个新 token | 显存带宽（GPU 内存读写） | 串行，主要瓶颈是读取 KV Cache |

`★ Insight ─────────────────────────────────────`
Prefill 阶段像"一口气读完一本书"（计算密集），Decode 阶段像"逐字写读后感"（带宽密集）。大部分推理时间花在 Decode 上，因为生成 100 个 token 就要做 100 次完整前向传播，每次都要从显存中读取所有模型权重。
`─────────────────────────────────────────────────`

## 二、量化（Quantization）

### 2.1 什么是量化？

量化的本质：**用更少的比特表示模型权重，减少显存占用和计算量。**

```
FP32（32位浮点）→ FP16（16位）→ INT8（8位整数）→ INT4（4位整数）
   4 字节/参数      2 字节/参数     1 字节/参数      0.5 字节/参数
```

**直观效果**：

| 精度 | 7B 模型权重大小 | 相对 FP16 |
|------|---------------|----------|
| FP32 | 28 GB | 2x |
| FP16 | 14 GB | 1x（基准） |
| INT8 | 7 GB | 0.5x |
| INT4 | 3.5 GB | 0.25x |

### 2.2 量化的基本原理

以 INT8 量化为例：

```
原始权重（FP16）：[0.234, -1.567, 0.089, 2.301, ...]
                          ↓
1. 找到最大值：max(|weights|) = 2.301
2. 计算缩放因子：scale = 2.301 / 127 = 0.0181
3. 量化：每个值除以 scale，四舍五入到整数
   [13, -86, 5, 127, ...]（INT8）
                          ↓
反量化（推理时）：
   每个整数值 × scale ≈ 还原为近似的浮点值
```

### 2.3 常见量化方法

| 方法 | 类型 | 量化对象 | 特点 |
|------|------|---------|------|
| **PTQ**（训练后量化） | 静态 | 权重 | 简单，不需要重新训练，效果略降 |
| **QAT**（量化感知训练） | 动态 | 权重 + 激活 | 训练时模拟量化效果，精度更好 |
| **GPTQ** | PTQ | 权重 | 逐层量化 + 校准数据，精度高 |
| **AWQ** | PTQ | 权重 | 保护重要权重通道，效果好 |
| **GGUF** | PTQ | 权重 | llama.cpp 格式，CPU 友好 |

### 2.4 GPTQ vs AWQ

这两种是目前最常用的权重量化方法：

| 维度 | GPTQ | AWQ |
|------|------|-----|
| 核心思路 | 逐层最小化量化误差 | 识别并保护重要权重通道 |
| 量化粒度 | 逐层 | 逐组（group） |
| 速度 | 较慢（需要校准数据） | 较快 |
| 效果（4-bit） | 好 | 略好 |
| 支持格式 | GPTQ、safetensors | AWQ |

### 2.5 量化的实际影响

```
7B 模型 + FP16 推理：需要 14 GB 显存 → RTX 4090（24GB）勉强能跑
7B 模型 + INT4 推理：需要 3.5 GB 显存 → RTX 3060（12GB）轻松能跑
13B 模型 + INT4 推理：需要 7 GB 显存 → RTX 4090 还能同时跑其他任务
```

`★ Insight ─────────────────────────────────────`
这和你 LoRA 笔记里的 QLoRA 直接对应：QLoRA = 4-bit 量化（NF4 格式）+ LoRA 微调。量化让你用更少显存**加载**模型，LoRA 让你用更少参数**训练**模型，两者结合就是 QLoRA 的核心思路。
`─────────────────────────────────────────────────`

## 三、KV Cache

### 3.1 为什么需要 KV Cache？

回顾 Self-Attention 的计算：每个 token 需要用自己的 Q 和所有之前 token 的 K、V 做计算。

**没有 KV Cache 时**：

```
生成第 5 个 token：
  计算 token5 的 Attention → 需要 k₁,v₁,k₂,v₂,k₃,v₃,k₄,v₄,k₅,v₅
  → 这些 K、V 是从 token1~5 的输入重新算出来的！

问题：token1~4 的 K、V 在之前生成时已经算过了，现在又重复计算一遍。
```

**有 KV Cache 时**：

```
生成第 1 个 token：计算并缓存 k₁, v₁
生成第 2 个 token：复用缓存的 k₁,v₁，只计算 k₂,v₂，然后缓存
生成第 3 个 token：复用 k₁,v₁,k₂,v₂，只计算 k₃,v₃
...

每次 Decode 只需要计算当前 token 的 K、V，其余从缓存读取
```

### 3.2 KV Cache 的显存计算

KV Cache 的大小取决于：

$$\text{KV Cache 大小} = 2 \times n_{\text{layers}} \times n_{\text{kv\_heads}} \times d_{\text{head}} \times \text{seq\_len} \times \text{batch\_size} \times \text{bytes}$$

以 Qwen2.5-7B 为例（GQA，8 个 KV head）：

| 参数 | 值 |
|------|-----|
| 层数 $n_{layers}$ | 28 |
| KV 头数 $n_{kv\_heads}$ | 8 |
| 每头维度 $d_{head}$ | 128 |
| 序列长度 | 4096 |
| 精度 | FP16（2 字节） |

$$\text{KV Cache} = 2 \times 28 \times 8 \times 128 \times 4096 \times 2 = 0.46 \text{ GB}$$

**注意**：KV Cache 随序列长度**线性增长**。如果上下文窗口是 128K token，KV Cache 会非常大。

### 3.3 KV Cache 的优化技术

| 技术 | 原理 | 效果 |
|------|------|------|
| **PagedAttention** | 像操作系统管理内存一样，将 KV Cache 分页存储，避免显存碎片 | vLLM 的核心创新，显存利用率提升 60%+ |
| **GQA** | 减少 KV 头数 | KV Cache 直接缩小为 MHA 的 $1/g$ |
| **KV Cache 量化** | 将 KV Cache 从 FP16 压缩到 INT8/FP8 | 显存减半，精度损失小 |
| **窗口注意力** | 只缓存最近 N 个 token 的 KV | 限制最大显存占用 |
| **KV Cache 淘汰** | 动态驱逐不重要的 KV 对 | 如 H2O、StreamingLLM |

### 3.4 PagedAttention（vLLM）

传统 KV Cache 的问题：预分配固定大小的连续显存块。

```
传统方式：预分配 4096 token 的连续显存
  实际用了 512 token → 浪费 3584 token 的显存空间
  多个请求各自预分配 → 大量显存碎片
```

PagedAttention 像虚拟内存一样管理 KV Cache：

```
逻辑上：连续的 KV 序列 [token1][token2][token3]...
物理上：分散在不同的显存页中，通过页表映射

优点：
- 按需分配，不浪费
- 多个请求共享相同前缀的 KV Cache（如系统提示词）
- 支持更大的 batch size → 吞吐量提升
```

## 四、投机解码（Speculative Decoding）

### 4.1 核心思想

> 用一个小模型快速"猜测"几个 token，然后用大模型一次性验证。如果猜对了，就跳过了大模型逐个生成的过程。

```
传统方式（大模型逐个生成）：
  大模型 → token₁ → 大模型 → token₂ → 大模型 → token₃ → ...
  （每步都要完整前向传播，慢）

投机解码：
  小模型快速猜：token₁, token₂, token₃, token₄
  大模型一次验证：四个 token 一起验证，接受猜对的部分
  （可能一次验证就生成了 3-4 个 token）
```

### 4.2 为什么有效？

| 对比 | 传统解码 | 投机解码 |
|------|---------|---------|
| 大模型调用次数 | 每个 token 1 次 | 多个 token 1 次 |
| 速度瓶颈 | 大模型推理速度 | 小模型 + 大模型验证 |
| 输出质量 | 基准 | **完全相同**（理论保证） |

**质量完全相同的保证**：投机解码的验证步骤保证，最终接受的 token 概率分布与大模型独立生成完全一致。这不是近似，是数学等价。

### 4.3 投机解码的流程

```
1. 小模型猜测 K 个 token：x₁, x₂, ..., x_K
2. 大模型一次性对这 K 个 token 做前向传播，得到每个位置的概率
3. 逐个验证：
   - x₁：如果大模型认为 x₁ 的概率足够高 → 接受，继续
   - x₂：如果大模型认为 x₂ 的概率不够高 → 拒绝，从大模型的分布中重新采样
   - 后续 token 全部丢弃
4. 返回接受的 token 序列（至少 1 个，最多 K+1 个）
```

## 六、代码示例

### 6.1 使用 vLLM 部署（PagedAttention + 量化）

```python
from vllm import LLM, SamplingParams

# 加载量化模型（GPTQ/AWQ 格式自动识别）
llm = LLM(
    model="Qwen/Qwen2.5-7B-AWQ",    # AWQ 量化版本
    quantization="awq",               # 量化方式
    max_model_len=8192,               # 最大上下文长度
    gpu_memory_utilization=0.9,       # GPU 显存利用率
)

# 采样参数
params = SamplingParams(
    temperature=0.7,
    top_p=0.9,
    max_tokens=512,
)

# 批量推理（vLLM 自动做 continuous batching）
prompts = ["什么是深度学习？", "解释量子计算", "RAG 的原理是什么？"]
outputs = llm.generate(prompts, params)

for output in outputs:
    print(output.outputs[0].text)
```

### 6.2 使用 llama.cpp（GGUF 格式，CPU 推理）

```python
from llama_cpp import Llama

# 加载 GGUF 量化模型（可以在纯 CPU 上运行）
llm = Llama(
    model_path="qwen2.5-7b-q4_k_m.gguf",  # 4-bit 量化
    n_ctx=4096,                              # 上下文长度
    n_threads=8,                             # CPU 线程数
)

# 推理
output = llm("什么是机器学习？", max_tokens=256)
print(output["choices"][0]["text"])
```

## 七、面试高频问题

### Q1：什么是量化？为什么要做量化？

> 量化是将模型权重从高精度（如 FP16）转换为低精度（如 INT4）的过程。好处：(1) 模型体积缩小 2-8 倍；(2) 显存占用大幅降低；(3) 低精度计算更快。一个 7B 模型从 FP16 的 14GB 缩小到 INT4 的 3.5GB，消费级显卡就能跑。

### Q2：GPTQ 和 AWQ 的区别？

> GPTQ 逐层量化，通过最小化每层的量化误差来保持精度，需要少量校准数据。AWQ 的核心发现是：权重中只有少数"显著权重"（salient weights）对模型效果影响大，量化时保护这些通道（对它们保持更高精度），整体效果更好。AWQ 通常比 GPTQ 精度略高且速度更快。

### Q3：什么是 KV Cache？为什么它对推理至关重要？

> KV Cache 缓存了 Attention 计算中之前 token 的 Key 和 Value，避免重复计算。没有 KV Cache，每次生成新 token 都要从头计算所有 token 的 K、V，计算量会随序列长度平方增长。有 KV Cache 后，每次 Decode 只计算当前 token 的 K、V，其余从缓存读取，计算量从 O(n²) 降到 O(n)。

### Q4：KV Cache 的显存占用怎么算？为什么长上下文是个挑战？

> KV Cache 大小 = 2 × 层数 × KV头数 × 每头维度 × 序列长度 × batch_size × 精度字节数。序列长度是线性因子，所以 128K 上下文比 4K 上下文的 KV Cache 大 32 倍。一个 7B 模型在 128K 上下文下，仅 KV Cache 就需要约 15GB 显存。

### Q5：投机解码为什么能加速推理且不损失质量？

> 投机解码用小模型快速生成 K 个候选 token，大模型一次性验证。数学上保证：接受的 token 的概率分布与大模型独立生成完全一致。加速的原因是：大模型一次前向传播可以验证多个 token，而不是每个 token 都做一次完整前向传播。但加速比取决于小模型的"猜对率"——对于简单、可预测的 token（如常见句式），猜对率高，加速明显。

### Q6：vLLM 的 PagedAttention 解决了什么问题？

> 传统 KV Cache 预分配连续显存块，导致两个问题：(1) 序列长度不确定时预留过多显存造成浪费；(2) 多个请求的显存碎片化严重。PagedAttention 借鉴操作系统的虚拟内存思想，将 KV Cache 分成固定大小的页，按需分配、动态管理。还支持相同前缀的 KV Cache 在多个请求间共享（如系统提示词），显存利用率提升 60%+。

## 八、总结

**三种推理优化技术一句话总结**：

| 技术 | 解决什么问题 | 核心思路 |
|------|------------|---------|
| **量化** | 模型太大，显存放不下 | 用更少的比特表示权重（FP16 → INT4） |
| **KV Cache** | Attention 计算重复，太慢 | 缓存已计算的 K、V，避免重复计算 |
| **投机解码** | 自回归生成太慢 | 小模型猜 + 大模型验证，一次生成多个 token |

**推理优化的完整技术栈**：

```
模型权重：量化（GPTQ/AWQ/GGUF）
注意力计算：KV Cache + PagedAttention
生成速度：投机解码
部署框架：vLLM / TGI / TensorRT-LLM
```
