# 长上下文技术

> Agent 让模型能使用工具，但还有一个基础能力需要突破——**长上下文**。标准大模型的上下文窗口通常是 4K-8K tokens，而实际应用中经常需要处理长文档（论文、代码库、法律合同）。长上下文技术让模型能处理 100K 甚至 1M+ tokens 的输入。

---

## 一、为什么需要长上下文

### 1.1 实际应用需求

| 场景 | 需要的上下文长度 | 说明 |
|------|----------------|------|
| **长文档理解** | 10K-100K | 论文、书籍、法律合同 |
| **代码库分析** | 100K+ | 理解整个项目的代码 |
| **多轮对话** | 10K-50K | 保持长对话的连贯性 |
| **RAG 增强** | 10K-50K | 检索多段相关文档 |
| **多模态理解** | 100K+ | 视频、长音频的理解 |

### 1.2 标准 Attention 的问题

```
标准 Self-Attention 的计算复杂度：O(n² × d)

n = 4K tokens  → 计算量：16M × d
n = 32K tokens → 计算量：1G × d（64 倍）
n = 128K tokens → 计算量：16G × d（1024 倍）

显存占用：O(n²)（需要存储注意力矩阵）
4K tokens → 16M 个注意力值
128K tokens → 16G 个注意力值（放不下！）
```

## 二、位置编码外推

### 2.1 问题：位置编码的长度限制

RoPE 位置编码在训练时见过的最大长度为 $L_{train}$，超过这个长度后，模型没见过这么远的位置，性能会急剧下降。

```
训练长度：4K tokens
推理长度：32K tokens
问题：位置 4096 之后的位置编码是"陌生的"
```

### 2.2 NTK-Aware Scaling

**核心思想**：调整 RoPE 的基频（base frequency），让位置编码的有效范围扩大。

```
原始 RoPE：
  频率 = 1 / (base^(2i/d))
  base = 10000

NTK-Aware Scaling：
  新 base = base × (scale_factor)^(d/(d-2))
  
  例如：4K → 32K（8 倍）
  新 base = 10000 × 8^(d/(d-2)) ≈ 10000 × 8 ≈ 80000
```

**YaRN（Yet another RoPE extensioN）**：

```
结合 NTK Scaling 和注意力缩放：
1. 对高频维度：不做缩放（保留局部位置信息）
2. 对低频维度：做 NTK Scaling（扩展远距离位置）
3. 对注意力分数：乘以温度系数（补偿分布变化）

效果：4K → 128K，性能下降 < 5%
```

### 2.3 实现示例

```python
def yarn_rope(dim, max_position_embeddings, base=10000, scale=8):
    """YaRN 位置编码缩放"""
    # 计算新的 base
    new_base = base * (scale ** (dim / (dim - 2)))
    
    # 生成频率
    freqs = 1.0 / (new_base ** (torch.arange(0, dim, 2).float() / dim))
    
    # 生成位置编码
    t = torch.arange(max_position_embeddings)
    freqs = torch.outer(t, freqs)
    
    # 计算 sin/cos
    emb = torch.cat([freqs, freqs], dim=-1)
    cos_cached = emb.cos()
    sin_cached = emb.sin()
    
    return cos_cached, sin_cached
```

## 三、高效 Attention 方法

### 3.1 Flash Attention

**核心思想**：利用 GPU 的内存层次（SRAM vs HBM），减少内存访问次数。

```
标准 Attention：
  1. 计算 QK^T → 存入 HBM（显存）
  2. 读取 QK^T → 计算 softmax → 存入 HBM
  3. 读取 softmax 结果 → 计算与 V 的乘积
  
  问题：QK^T 矩阵很大（n×n），频繁读写 HBM

Flash Attention：
  1. 把 Q、K、V 分块加载到 SRAM（缓存）
  2. 在 SRAM 中完成所有计算
  3. 直接输出最终结果到 HBM
  
  优势：避免存储 n×n 的注意力矩阵，减少 HBM 访问
```

**效果**：

| 指标 | 标准 Attention | Flash Attention |
|------|--------------|-----------------|
| 显存占用 | O(n²) | O(n) |
| 计算速度 | 基准 | 2-4x 加速 |
| 支持长度 | 受限于显存 | 大幅扩展 |

### 3.2 Sliding Window Attention

**核心思想**：每个 token 只关注最近的 $W$ 个 token。

```
标准 Attention：
  token₁₀₀ 关注 [token₁, token₂, ..., token₁₀₀]

Sliding Window（W=256）：
  token₁₀₀ 关注 [token₇₅, token₇₆, ..., token₁₀₀]
  
显存占用：固定为 W × d，不随序列增长
```

**代价**：丢失长距离依赖信息。

**改进：Longformer 的 Dilated Sliding Window**：

```
扩大窗口范围，但跳过一些 token（扩张注意力）

窗口大小 W=256，扩张率 d=4：
  token₁₀₀ 关注 [token₄, token₈, token₁₂, ..., token₁₀₀]
                    ↑     ↑     ↑
                  跳过   跳过   跳过
```

### 3.3 Sparse Attention

**核心思想**：只计算部分位置的注意力，跳过不重要的位置。

```
全局 + 局部模式：

token₁₀₀ 的注意力：
  - 全局 token：token₁, token₂, token₃（固定关注）
  - 局部 token：token₉₀, token₉₁, ..., token₁₀₀（最近 10 个）
  - 跳过：token₄ - token₈₉（不计算）

显存占用：O(n × k)，k 是每个 token 关注的 token 数
```

### 3.4 Linear Attention

**核心思想**：用核函数近似 softmax，把复杂度从 O(n²) 降到 O(n)。

```
标准 Attention：
  Attention = softmax(QK^T/√d) × V
  
  复杂度：O(n² × d)

Linear Attention：
  Attention = φ(Q) × (φ(K)^T × V)
  
  先算 φ(K)^T × V（d×d 矩阵），再与 φ(Q) 相乘
  复杂度：O(n × d²)
  
  当 d << n 时，Linear Attention 更快
```

**代价**：精度损失（softmax 近似不完美）。

## 四、KV Cache 优化

### 4.1 问题：长序列的 KV Cache

```
128K tokens 的 KV Cache（LLaMA 70B）：
  每 token：8 KB
  总计：128K × 8 KB = 1 GB（单条序列！）

批量推理（batch=32）：
  32 × 1 GB = 32 GB（只 KV Cache 就超过显存）
```

### 4.2 解决方案

| 方案 | 思路 | 效果 |
|------|------|------|
| **GQA/MQA** | 多 Q 头共享 KV | KV Cache 减 4-8x |
| **KV Cache 量化** | INT8/INT4 量化 | KV Cache 减 2-4x |
| **滑动窗口** | 只保留最近 W 个 | KV Cache 固定大小 |
| **StreamingLLM** | 保留开头 + 最近 | KV Cache 固定大小 |
| **PagedAttention** | 动态分页 | 消除碎片化 |

### 4.3 StreamingLLM 的实现

```python
class StreamingLLM:
    def __init__(self, sink_size=4, window_size=1020):
        self.sink_size = sink_size  # 保留的开头 token 数
        self.window_size = window_size  # 保留的最近 token 数
    
    def process_kv_cache(self, k_cache, v_cache):
        """处理 KV Cache，只保留开头和最近"""
        total_len = k_cache.shape[0]
        
        if total_len <= self.sink_size + self.window_size:
            # 还没超过限制，不处理
            return k_cache, v_cache
        
        # 保留开头（Attention Sink）
        k_sink = k_cache[:self.sink_size]
        v_sink = v_cache[:self.sink_size]
        
        # 保留最近
        k_window = k_cache[-self.window_size:]
        v_window = v_cache[-self.window_size:]
        
        # 拼接
        k_cache = torch.cat([k_sink, k_window], dim=0)
        v_cache = torch.cat([v_sink, v_window], dim=0)
        
        return k_cache, v_cache
```

## 五、分块处理

### 5.1 文档分块策略

```
长文档分块：

原始文档（100K tokens）
    ↓
分成 10 个块，每块 10K tokens
    ↓
每个块单独处理
    ↓
合并结果
```

**分块策略**：

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| **固定长度** | 按 token 数分块 | 简单场景 |
| **语义分块** | 按段落/章节分块 | 保持语义完整性 |
| **重叠分块** | 块之间有重叠 | 保持上下文连贯 |
| **递归分块** | 先大块再细分 | 复杂文档 |

### 5.2 Map-Reduce 模式

```
Map 阶段：
  块1 → LLM → 摘要1
  块2 → LLM → 摘要2
  块3 → LLM → 摘要3
  ...

Reduce 阶段：
  [摘要1, 摘要2, 摘要3, ...] → LLM → 最终答案
```

### 5.3 Window 模式

```
滑动窗口处理：

块1: [token₁ - token₁₀K]  → LLM → 中间状态1
块2: [token₅K - token₁₅K] → LLM → 中间状态2（重叠 5K）
块3: [token₁₀K - token₂₀K] → LLM → 中间状态3（重叠 5K）
...

每个块都基于前一块的中间状态继续处理
```

## 六、模型架构创新

### 6.1 Ring Attention

**核心思想**：把长序列分布到多张卡上，每张卡只处理一段，通过环形通信交换 KV。

```
4 张卡，128K tokens：

GPU 0: tokens 0-32K（自己的 Q）
GPU 1: tokens 32K-64K
GPU 2: tokens 64K-96K
GPU 3: tokens 96K-128K

Ring 通信：
GPU 0 → GPU 1 → GPU 2 → GPU 3 → GPU 0
（每张卡轮流接收其他卡的 KV，计算部分注意力）

效果：每张卡只需要 O(32K) 的显存，但能处理 128K tokens
```

### 6.2 Context Parallelism

```
类似 Ring Attention，但优化通信：

1. 把 Q、K、V 按序列维度切分到多张卡
2. 每张卡计算自己那段的注意力
3. 通过 AllGather 交换 KV
4. 合并结果

优势：支持超长上下文（1M+ tokens）
```

### 6.3 Mixture of Contexts

**核心思想**：不是所有 token 都需要长上下文，只有部分 token 需要关注远处。

```
输入 tokens 分类：
  - 局部 token：只需要关注附近（如标点、停用词）
  - 全局 token：需要关注远处（如主语、关键词）

对局部 token：用 Sliding Window
对全局 token：用 Full Attention

效果：兼顾效率和效果
```

## 八、面试高频问题

### Q1：为什么需要长上下文技术？

> 实际应用中经常需要处理超过模型训练长度的文本：长文档理解（论文、法律合同 10K-100K tokens）、代码库分析（100K+ tokens）、多轮长对话（10K-50K tokens）、RAG 多文档检索。标准模型上下文窗口有限（4K-8K），超过后性能急剧下降，需要长上下文技术来扩展。

### Q2：位置编码如何支持更长的序列？

> RoPE 位置编码在训练时见过的最大长度有限，超过后性能下降。解决方案：(1) **NTK-Aware Scaling**——调整 RoPE 基频，让有效范围扩大；(2) **YaRN**——结合 NTK Scaling 和注意力温度系数，4K→128K 性能下降 < 5%；(3) **ALiBi**——用线性偏置代替绝对位置，天然支持外推。

### Q3：Flash Attention 是如何加速的？

> Flash Attention 利用 GPU 的内存层次（SRAM 快但小，HBM 慢但大）优化：(1) 把 Q、K、V 分块加载到 SRAM；(2) 在 SRAM 中完成所有注意力计算；(3) 直接输出最终结果到 HBM。核心优势是避免存储 n×n 的注意力矩阵（从 O(n²) 降到 O(n)），减少 HBM 访问次数，实现 2-4x 加速。

### Q4：Sliding Window Attention 的原理和代价是什么？

> Sliding Window 让每个 token 只关注最近的 W 个 token（如 256），而不是全部历史。优点：KV Cache 大小固定为 W×d，不随序列增长；计算量从 O(n²) 降到 O(n×W)。代价：丢失长距离依赖信息（token₁₀₀ 无法直接关注 token₁）。改进：Longformer 用扩张注意力扩大范围；实际中常与全局 token（固定关注开头几个 token）结合使用。

### Q5：如何处理超长文档（100K+ tokens）？

> 常用方法：(1) **分块处理**——把文档分成小块，每块单独处理；(2) **Map-Reduce**——每块生成摘要，再合并摘要得到答案；(3) **滑动窗口**——块之间有重叠，保持连贯；(4) **RAG**——检索相关块，避免处理全部内容；(5) **Ring Attention**——多卡分布式处理。注意 "Lost in the Middle" 问题：重要信息放在开头/结尾效果更好。

### Q6：长上下文模型有哪些常见陷阱？

> (1) **Lost in the Middle**——模型忽略中间部分的信息，需要把重要信息放在开头/结尾；(2) **注意力稀释**——长序列中注意力被分散，检索相关片段比纯长上下文更可靠；(3) **幻觉增加**——长上下文更容易产生幻觉，需要结合检索验证；(4) **计算成本高**——长序列推理很慢，需要分块处理或缓存中间结果。

## 九、总结

| 技术 | 原理 | 适用场景 |
|------|------|---------|
| NTK/YaRN | 调整 RoPE 基频 | 位置编码外推 |
| Flash Attention | 优化内存访问 | 加速 + 省显存 |
| Sliding Window | 只关注最近 W 个 token | 固定 KV Cache |
| Ring Attention | 多卡分布式处理 | 超长序列 |
| 分块处理 | 文档切分 + 合并 | 超长文档 |

**一句话记忆**：

> 长上下文就是"扩展 AI 的短期记忆"——让它能同时处理更多信息。Flash Attention 是"优化记忆过程"（更快），NTK/YaRN 是"扩展记忆容量"（更长），分块处理是"分批记忆"（化整为零）。
